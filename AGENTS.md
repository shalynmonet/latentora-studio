## Latentora architecture rules
- All Meta Model API calls live in `src/lib/meta.server.ts` (Made for Me prompts in `made-for-me.server.ts`) and are invoked only from server functions in `src/lib/*.functions.ts`; the key comes from the `MODEL_API_KEY` secret. Why: keeps the key server-side and API usage in one place.
- No sign-in: data is scoped by a random workspace id stored in localStorage; tables have RLS on with no policies and are accessed only via the service-role client inside server functions. Why: frictionless judging/demo while keeping the Data API closed.
- Every AI-derived record stores a `source` (`meta_live` | `demo_sample` | `offline_heuristic`) and the UI must show it. Why: never disguise sample or fallback output as live Meta results.
- Proof Lab scoring and Atlas status changes are deterministic TypeScript (`scoring.ts`, `challenge-rules.ts`, `atlas.ts`) with tests in `src/lib/scoring.test.ts`; Muse Spark may only propose designed-challenge specs, which `sanitizeSpec` validates before saving, and SAM output only contributes observations. Why: no fabricated or AI-inferred physical claims.
- Photos used for vision boards are sent to Muse Image `/images/edits` per request and never stored; boards record `from_photo`. Why: avoid keeping face photos.
- Media goes to the private `latentora-media` bucket as `storage:<path>` and is signed on read; bundled demo images use `asset:<name>`. Why: workspace policy blocks public buckets.
- Explore merges free public listing feeds (Remotive, Jobicy, Freelancer.com, OpenTrain, Terac via its public Ashby board) via `listings.server.ts` into one list; each source is cached per query in `job_cache` with its own window from `PROVIDERS` (Remotive 12h). Only official/public endpoints — no scraping or unofficial APIs (Upwork, Twine, Mercor stay paste-in). Why: respect source terms and Remotive's ~4 requests/day ask.
- Explore's "Picked for you" list (`suggestOpportunities`) searches the same cached feeds with terms from `pickQueries` (the person's own capability map), lets Muse Spark choose only from that pool by ref, falls back to labelled keyword ranking, and caches per capability-map version in `job_cache` (`picks:` keys). Why: pre-filled, real listings without extra feed calls or invented opportunities.
- Made for Me: Muse Spark must cite evidence ids built server-side from the person's own words, stories and Atlas; `made-for-me.ts` drops uncited ideas, derives fact/preference/hypothesis labels, always appends fixed accessibility requirements per chosen preference, and assembles the build prompt from approved details only (tests in `made-for-me.test.ts`). Judge-demo replays come from `made-for-me-recorded.json` and are labelled as not live. Why: traceable personalisation without fabricated or leaked personal details.
- Build with Muse: `build-with-muse.server.ts` asks Muse Wonder (`META_MODELS.code`, Chat Completions) for a self-contained static web app from the approved blueprint; `build-rules.ts` sanitizes paths, parses JS with acorn (never executes), rejects external resources, and flags missing preference signals (tests in `build-rules.test.ts`); one automatic repair pass; the zip is built in the browser. Why: real downloadable code without running untrusted code or adding hosting/agent infrastructure.
- Résumé discovery: the browser reads the file (`resume-extract.ts`: DOCX via JSZip, PDF text via unpdf) and PDFs also go to Muse Spark natively; `resume.functions.ts` never stores the file or full text, only quoted passages, findings and the user's review. `resume-rules.ts` drops quotes not found in the document text, downgrades unevidenced findings, strips protected attributes, and merges only confirmed findings into the analysis via `analysis.server.ts` `loadEffectiveAnalysis` (the single read path for capabilities; tests in `resume-rules.test.ts`). Why: traceable, user-approved résumé evidence that reaches every feature without duplicating or weakening story evidence.
- The main capability analysis (`analyzeStories`) runs with a résumé alone or 3+ stories; it reads only stored quoted passages/roles via `resumeForAnalysis`, reuses confirmed finding names so the merge dedupes, and drops rejected findings. Why: a résumé is enough to start, without re-reading the original file or overriding the person's review.
